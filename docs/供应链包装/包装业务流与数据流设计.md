# 包装业务流与数据流设计

> 三条设计主线：业务分三段（计划 / 执行 / 结算），数据分三层（主数据 / 交易 / 快照），层级分两类（规格层级 / 实例层级）。

## 一、业务流设计：三段九事件（三流合一）

| | ① 计划段 · 订单确认/发运计划 | ② 入厂段 · 收货/翻包 | ③ 厂内段 · 线边/成品包装 | ④ 出厂段 · 装车/报关 |
|---|---|---|---|---|
| **实物流** | 订单/预测锁定，确认包装方案（客户规格优先） | 来料收货上架，按需翻包转换 | 线边配送·生产，成品装箱/码托，贴标签入库 | 装车拼载·封柜，报关·发运，客户签收/回收 |
| **单据流** | 销售订单/发运计划，包装方案确认单，包装BOM与包材请购 | 收货单（按包装量），翻包工单/转换单，异常让步接收单 | 领料单/看板，装箱单 Packing List，成品入库单 | 装车单·报关单，舱单/ASN 预报，运费对账单 |
| **数据流** | 理论数据冻结，Pack Spec 版本发布，装载单元链定义 | 扫码校验标准包装量，翻包后重称重，生成内部包装编码 | 箱码/托码生成，实测毛净重回写，偏差告警→复核工单 | 装载快照（冻结），计费重/报关毛净重，差异留痕 |

**分界线（Gate）**：计划段结束时「包装规格版本 + 发运计划」必须双锁定，这是理论数据唯一合法的时间窗；执行段只做校验和实例生成，不得修改规格；结算段只读快照，不读实时主数据。

## 二、数据流设计：主数据 → 交易 → 快照三层

```
① 主数据层 PKG-SPEC（层级树 + 场景版本 + 理论/实测双字段 + 包装BOM）
        ↓ 读：按出货日/收货日取生效版本
② 交易层：ERP(订单包装量/包材请购) | WMS(收货校验/翻包转换) | MES(箱码托码/实测称重) | TMS(装载单元/装载率)
        ↓ 写：冻结为不可变快照（版本+时间戳+取值明细）
③ 快照层：装载快照 / 单据快照 —— 之后的主数据变更不得回溯影响已发生单据
        ↓ 取：对外单据与结算一律读快照
④ 消费方：WMS作业指令 | TMS装车单 | 装箱单/发票 | 关务申报 | 运费结算/对账
```

**最容易出事的地方**：下游直接用主数据实时值生成历史单据。包装规格升版后，三个月前的报关单、运费单会「跟着变」，对账对不上。快照不是可选优化项，是必须项。

## 三、包装层级设计：规格层级与实例层级分开

### 3.1 层级模型

| 层级 | 编码示例 | 数量关系 | 承载关键属性 | 谁生成/何时 | 数据性质 |
|---|---|---|---|---|---|
| 单件 EA | `ITEM-SKU001` | 1 | 单件净重、尺寸、防护等级 | PLM/ERP 建品时 | 常驻主数据 |
| 内包装 INNER | `PKG-INT-SKU001-01` | 1 内包 = n 单件 | 内包净重、缓冲/防静电/防锈 | 包装工程 | 常驻主数据（随版本） |
| 箱 CASE | `PKG-SUP-SKU001-01` | 1 箱 = n 内包 | 外箱尺寸、SPQ、堆码层数、可叠性 | 包装工程 | 常驻主数据（随版本） |
| 托盘 PLT | `PLT-1210-A` | 1 托 = n 箱 | 托型、每托箱数、托高、托重 | 包装工程 | 常驻主数据（随版本） |
| 托盘实例 LPN | `LPN-SSCC-0001` | 1 LPN 装若干箱 | 实际箱数、实测毛重、批次、库位 | WMS/MES 装箱时 | 单次实例（随批次） |
| 柜/车 SHIP | `SHIP-装车号` | 1 车 = n LPN | 装载率、卸货顺序、封号、计费重 | TMS 拼载时 | 单次实例 |

前四层是「规格」，一套 SKU 一套（可多场景多版本）；后两层是「实例」，一托一码、一车一码。混淆这两类数据是 WMS 与主数据对不上的根本原因。

### 3.2 关联主数据的方式

| 设计要素 | 做法 |
|---|---|
| 表结构 | 单表树形：`PKG_ID / PARENT_PKG_ID / LEVEL / QTY_PER_PARENT`，自关联递归 |
| 唯一约束 | `PKG_ID + 版本` 唯一；同一 `SKU + 场景 + 层级` 只允许一个「生效中」版本 |
| 换算集中定义 | `QTY_PER_PARENT` 是唯一换算源（EA→箱→托），所有系统读它，禁止各自维护 |
| 属性继承规则 | 重量自下而上汇总（子层净重×数量+皮重），尺寸自上而下约束（子层堆码 ≤ 父层容积/承重） |
| 场景维度 | 同一 SKU 可有 SUP/INT/RTN/FIN/CUS 五条并行链；出货以 CUS 优先，无则退回 FIN |
| 包装BOM | 箱/托层挂包材子项（箱、内衬、标签、缠绕膜、托盘），供 ERP 做包材 MRP |
| 版本与生效 | 变更走升版 + 生效日期；旧版本只读保留 |
| 校验方向 | 向上校验汇总一致性，向下校验物理可行性（堆码、承重、车辆内尺寸） |

### 3.3 编码规则

`PKG-{场景}-{SKU}-{层级序号}` + 独立版本字段。例：`PKG-FIN-SKU001-03`。版本单独存 `VER`，不要把版本拼进编码。

### 各系统的核心诉求

| 系统 | 核心诉求 | 字段重点 |
|---|---|---|
| WMS | 空间与作业效率 | 层级、SPQ、每托箱数、堆码、可叠、库位容积、拆零与混装、皮重 |
| TMS | 一次能装多少、装得下且不被压坏 | 毛重、外形尺寸、体积、可叠/承重、装载单元链、卸货顺序、危险品温控 |
| 装箱单 | 证明装了什么、几件、多重 | 箱号/托号（SSCC）、件数、每箱数量、净重、毛重、体积、唛头、原产地 |
| 关务 | 法定口径申报与合规 | 法定净重/毛重、件数、包装种类代码、法定计量单位、IPPC、原产地、危险品 UN |
| MES | 装箱动作正确性与可追溯 | 箱码/托码层级、SPQ、批次与序列号、客户标签、实测称重 |
| ERP/EDI | 库存单位、成本、包材采购 | 包装编码版本、SPQ、包装BOM、毛净皮重、循环资产、SSCC/GTIN |

## 五、八条设计红线

1. **规格与实例分开存**：主数据管规格，LPN/SSCC 管实例
2. **换算只有一个源**：换算率只能在包装主数据维护
3. **三个重量三个用途**：净重报关、毛重运输承重、体积重计费，独立存储
4. **对外单据必须读快照**：历史单据不随主数据升版变化
5. **一个 SKU 多场景多版本，但要唯一生效**：靠生效日期而非状态位控制
6. **关务字段单独成组**：法定口径与物流口径不同
7. **翻包必须生成新编码**：否则数据链断裂，成本、损耗、皮重全部失真
8. **理论值缺失要阻断**：不能用默认值兜底，默认值会静默污染下游拼载与报关数据

## 六、落地节奏

第一步「层级树 + 场景版本 + 换算率」→ 第二步 WMS 收货与翻包（实例编码跑通）→ 第三步 TMS 拼载与快照 → 第四步关务和结算。倒着做一定返工。
