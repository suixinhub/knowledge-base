# 操作手册

这份手册按"真的要动手时才查"的方式组织：先给三条最快路径，再给逐项操作步骤，最后是故障排查和速查表。

---

## 一、三种使用方式，先选一条

| 方式 | 适合场景 | 要准备什么 | 步骤数 |
|---|---|---|---|
| **A. 让我改** | 任何情况，尤其是批量改动、排版、转格式 | 无 | 说一句话 |
| **B. GitHub 网页编辑** | 手机上临时改个错字、加一段话 | 浏览器 | 5 步 |
| **C. 本地编辑器 + 命令行** | 长期写作、大量新增、想本地预览 | Git + 编辑器（可选 Python） | 一次配置，之后 3 步 |

大多数人最终会混用 A 和 B。C 适合需要认真写长文档的时候。

---

## 二、方式 A：让我改（零门槛）

直接把需求说清楚就行，例如：

- "在供应链包装分类下新增一篇《四类包装编码规则》，内容按 XXX 组织"
- "把 B站那份报告里的播放量表格更新成最新数据"
- "所有文档末尾加一句'最后更新于 2026-11'"
- "把这篇 PDF 转成 Markdown 放进资料分类"

我做的事：改文件 → 更新 `mkdocs.yml` 的导航 → 提交 → 推送 → 确认 Actions 构建成功 → 把网址给你。

**你只需要做一件事**：如果内容涉及敏感信息，先跟我说"这里面有公司数据"，我会建议放私有仓库或脱敏。

---

## 三、方式 B：GitHub 网页编辑

适合"手机上发现个错字，立刻改掉"。

### 新增一篇文档

1. 打开 https://github.com/suixinhub/knowledge-base
2. 进入目标分类目录，例如 `docs/供应链包装/`
3. 右上角 **Add file → Create new file**
4. 文件名填 `四类包装编码规则.md`（**必须带 `.md`**，中文名可用）
5. 在编辑区写内容，第一行写 `# 四类包装编码规则`
6. 页面底部 **Commit changes** → 选 **Commit directly to the main branch** → 确认
7. **关键一步**：打开根目录的 `mkdocs.yml`，点右上角铅笔图标编辑，在 `nav` 里对应分类下加一行：
   ```yaml
       - 四类包装编码规则: 供应链包装/四类包装编码规则.md
   ```
   **注意缩进必须和相邻行完全一致（空格数相同），YAML 对缩进敏感。**
8. 再次 Commit。约 1 分钟后网站更新。

### 修改已有文档

1. 进入那个页面在仓库里对应的 `.md` 文件
2. 右上角铅笔图标（Edit this file）
3. 改完 → Commit changes → 直接提交到 main
4. 无需改 `nav`（除非改了文件名）

### 上传图片/PDF

1. 进入 `docs/assets/img/`（图片）或 `docs/assets/pdf/`（PDF）
2. **Add file → Upload files** → 拖入文件 → Commit
3. 在文档里引用：
   - 图片：`![说明文字](../assets/img/文件名.png)`
   - PDF 下载链接：`[下载 PDF](../assets/pdf/文件名.pdf)`
   - **路径里的 `../` 数量取决于文档所在层级**：`docs/分类/文档.md` 用一层 `../`，`docs/文档.md` 直接用 `assets/...`

## 四、方式 C：本地写作（推荐长期使用）

### 一次性配置

```bash
# 1. 确认 git 已安装
git --version

# 2. 克隆仓库到本地（换成你想要的目录）
cd C:/Users/遂意/WorkBuddy/Claw
git clone https://github.com/suixinhub/knowledge-base.git
cd knowledge-base

# 3. 配置提交身份（只需一次）
git config user.name "Suixinhub"
git config user.email "51818835+suixinhub@users.noreply.github.com"

# 4. （可选）装本地预览环境，需要 Python 3.8+
pip install -r requirements.txt
```

### 日常写作三步

```bash
# 1. 开始写之前，先拉最新（避免和别人/别的设备改冲突）
git pull

# 2.（用编辑器写文件，或 mkdocs serve 边写边看）

# 3. 提交并推送
git add -A
git commit -m "docs: 新增四类包装编码规则"
git push
```

推送成功后 1~2 分钟网站更新。

### 本地预览（改了立刻看到效果）

```bash
mkdocs serve
```

打开 http://127.0.0.1:8000 ，**保存文件后浏览器自动刷新**。这是写长文档时最舒服的方式——不用等云端构建。

按 `Ctrl+C` 停止。

### 用什么编辑器

| 编辑器 | 优势 | 适合 |
|---|---|---|
| VS Code | 免费、Markdown 预览、Git 面板可视化 | 通用首选 |
| Typora | 所见即所得，写作体验最好 | 专注写字 |
| Obsidian | 直接把 `docs/` 当笔记库打开，也能看双链 | 已习惯 Obsidian 的话 |
| 记事本 | 无 | 应急 |

## 五、目录与命名规范

保持结构可预测，比"好看"重要得多。

```
knowledge-base/
├── mkdocs.yml                    # 网站配置（导航、主题）
├── requirements.txt              # 构建依赖
├── docs/                         # ← 所有内容只放这里
│   ├── index.md                  # 首页
│   ├── assets/                   # 附件
│   │   ├── img/                  # 图片
│   │   └── pdf/                  # PDF
│   ├── 供应链包装/
│   │   ├── index.md              # 该分类概览（必须有）
│   │   └── 包装主数据清单与数据流转.md
│   ├── 自媒体运营/
│   └── 关于/
└── .github/workflows/ci.yml      # 自动部署（不要改）
```

| 规则 | 说明 |
|---|---|
| 分类 = 文件夹 | 一个文件夹一个主题域，必配一个 `index.md` 作概览 |
| 文件名 = 页面 | 用中文没问题，但**别用空格和特殊符号**（`（）`、`、`、`#` 都可能出问题） |
| 文件名即标题首选 | 文件名和页面 H1 保持一致，减少认知负担 |
| 一篇一个主题 | 超过 3000 字的文档考虑拆分，检索命中率更高 |
| 分类不超过两级 | `docs/A/B/file.md` 可以，再深就别扭了；需要更细用标签 |
| 不要建 `docs/其他/` 这类垃圾桶 | 分类不清说明还没想清楚，先放 `资料/` 并尽快归类 |

## 六、Markdown 写作要点

### 常用语法

| 想要 | 写法 |
|---|---|
| 一级标题（每篇只用一次，放第一行） | `# 标题` |
| 二/三级标题 | `## 标题` / `### 标题` |
| 加粗 / 行内代码 | `**粗体**` / `` `代码` `` |
| 无序 / 有序列表 | `- 项` / `1. 项` |
| 表格 | 见下方示例 |
| 引用块 | `> 引用内容` |
| 提示框（主题支持） | `!!! note "标题"` 后接缩进 4 空格的正文 |
| 代码块 | 三个反引号 + 语言名 |
| 分割线 | `---` |
| 站内链接 | `[文字](相对路径.md)` |
| 外部链接 | `[文字](https://...)` |

### 表格示例

```markdown
| 字段 | 类型 | 说明 |
|---|---|---|
| 包装编码 | 文本 | 主键，唯一 |
| 毛重 | 数值 | 单位 kg，保留三位小数 |
```

表格前后**各留一个空行**，否则不渲染。

### 提示框示例

```markdown
!!! warning "注意"
    这段缩进必须是 4 个空格，内容才会进框里。

!!! tip "技巧"
    三种类型最常用：note / tip / warning。
```

### 三个容易踩的格式坑

1. **标题层级不要跳级**。`#` 之后直接 `###` 会让右侧目录（TOC）结构错乱。
2. **中文标点后紧跟英文时要留空格**，例如"用 PDF 导出"而不是"用PDF导出"——不影响渲染，但影响阅读节奏。
3. **不要手写 HTML 调样式**。要改样子改 `mkdocs.yml`，正文里塞 `<div style="...">` 会让全站风格失控。

## 七、导航（`nav`）怎么改

`mkdocs.yml` 里的 `nav` 决定**左侧/顶部导航的顺序和层级**。这是唯一需要手改配置的地方。

```yaml
nav:
  - 首页: index.md
  - 供应链包装:                          # 分类名，冒号后空着表示是分组
      - 概览: 供应链包装/index.md        # 缩进 6 空格
      - 包装主数据清单与数据流转: 供应链包装/包装主数据清单与数据流转.md
  - 关于本库:
      - 概览: 关于/index.md
      - 原理与架构: 关于/原理与架构.md
```

规则：

- **缩进用空格，不用 Tab**。每级 2 个空格。缩进错了整站构建失败。
- **冒号后必须有一个空格**。`- 概览: xxx.md` ✅；`- 概览:xxx.md` ❌。
- 路径**相对于 `docs/`**，不要写 `docs/xxx.md`。
- 同一篇文档可以出现在多个导航位置（但没必要）。
- 想隐藏某页的导航入口：从 `nav` 里删掉即可，文件保留仍可通过 URL 访问。

**改错了会怎样**：Actions 构建报错，网站保持上一次成功的版本不变（不会变成白屏）。看 Actions 日志里 `mkdocs build` 那一步的报错行号即可定位。

## 八、提交信息怎么写

不用严格遵循规范，但写清楚了以后回看有价值：

| 前缀 | 用于 | 示例 |
|---|---|---|
| `docs:` | 新增/修改内容 | `docs: 新增四类包装编码规则` |
| `fix:` | 修错字、修链接 | `fix: 修正包装主数据表中的毛重公式` |
| `style:` | 只调格式不动内容 | `style: 统一表格对齐方式` |
| `chore:` | 配置、依赖、工作流 | `chore: 升级 mkdocs-material 版本` |
| `refactor:` | 重组目录结构 | `refactor: 供应链包装拆成两个子分类` |

## 九、查看部署结果

三种方式，从快到细：

1. **直接刷网站**：https://suixinhub.github.io/knowledge-base/ ——最快，但可能要等 1~2 分钟。
2. **看 Actions**：仓库顶部 **Actions** 标签 → 最新一条记录。
   - 🟢 绿勾 = 成功
   - 🟡 黄点 = 正在跑
   - 🔴 红叉 = 失败，点进去看 `mkdocs gh-deploy` 那一步的日志
3. **看 gh-pages 分支**：仓库分支下拉里切到 `gh-pages`，能看到生成的 `index.html`、`search/` 等文件。**这是产物，不要手改。**

一次成功构建的典型耗时是 20~60 秒，其中大头是 `pip install` 的依赖安装。

## 十、故障排查

按"现象 → 原因 → 修法"查。

| 现象 | 最可能的原因 | 怎么修 |
|---|---|---|
| 网站还是旧内容 | Pages CDN 还没刷新 | 等 1~2 分钟；浏览器强制刷新 `Ctrl+F5` |
| Actions 红叉，日志报 `YAML` 错误 | `mkdocs.yml` 缩进或冒号空格错了 | 按日志给的行号检查 `nav` 缩进，每级 2 空格 |
| Actions 红叉，日志报 `not found` | `nav` 里写的路径和实际文件名不一致（含中文/大小写差异） | 对照 `docs/` 里真实文件名逐字核对 |
| 页面能通过链接打开，但导航里没有 | 新建文件没登记进 `nav` | 补 `nav` 一行 |
| 访问某页 404 | 文件名含空格或特殊符号，URL 编码失败 | 重命名为纯中文/英文/数字/短横线 |
| 搜索搜不到新内容 | 索引文件还没重建，或浏览器缓存了旧索引 | 等构建完成；强制刷新；仍不行看 `docs/` 里是否有该文件 |
| 中文搜索效果差 | `plugins.search.lang` 缺少 `zh` | 确认配置里有 `- zh` |
| 图片显示不出来 | 相对路径 `../` 层数不对 | `docs/分类/文件.md` 用 `../assets/...`；`docs/文件.md` 用 `assets/...` |
| `git push` 报 `Failed to connect` / 超时 | 本地代理拦截了 git 的 443 连接 | 用绕过代理的写法：见下方命令 |
| `git push` 报 `rejected` | 远程有本地没有的提交（网页上改过） | 先 `git pull --rebase`，再 `git push` |
| `git push` 要求账号密码 | 凭据过期 | 用 GitHub Personal Access Token 当密码；或直接找我代推 |
| 本地 `mkdocs serve` 报错 | 没装依赖或 Python 版本过低 | `pip install -r requirements.txt`；Python 需 3.8+ |
| 表格没渲染成表格 | 表格前后缺空行 | 前后各加一个空行 |

### 绕过代理的推送命令（这个环境常遇到）

```bash
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY \
  GIT_TERMINAL_PROMPT=0 git -c http.proxy= push origin main
```

含义：临时清掉代理相关的环境变量，并显式把 git 的代理设为空，直连 GitHub。

### 彻底回滚到上一次发布

```bash
git log --oneline -5      # 找到上一次正常的提交号
git revert <提交号>        # 生成一个反向提交（比 reset 安全，保留历史）
git push
```

如果只是单篇文档改坏了：

```bash
git checkout HEAD~1 -- docs/某篇文档.md
git commit -m "fix: 回滚某篇文档"
git push
```

## 十一、备份与恢复

**你不需要额外做备份**——每次 `git push` 已经是一份完整快照，GitHub 上也留有全部历史。但如果想要冗余：

| 需求 | 做法 |
|---|---|
| 换电脑 | `git clone` 到新机器，2 分钟恢复全部内容与历史 |
| 本地留一份离线副本 | 定期 `git pull`，或直接复制整个文件夹 |
| 怕 GitHub 账号出问题 | 在另一处（GitLab / Gitee / 本地 NAS）加一个 remote，`git push` 同时推两边 |
| 想导出成 PDF 分发给别人 | `mkdocs build` 后用浏览器逐页打印，或用 `mkdocs-pdf-export-plugin` |

**恢复被误删的文件**：

```bash
git log --diff-filter=D --summary    # 找到删除该文件的提交
git checkout <提交号>^ -- docs/被删的文件.md
```

## 十二、想改网站的样子

全部在 `mkdocs.yml`，改完推送即生效（不需要碰任何正文）。

| 想改什么 | 改哪里 |
|---|---|
| 站点名称 | `site_name` |
| 配色主色 | `theme.palette[].primary`（可选 indigo / blue / teal / green / purple 等） |
| 深浅色切换 | `theme.palette` 里的 `slate` 那一段 |
| 顶部横向导航 | `theme.features` 里的 `navigation.tabs`（删掉就变成侧边栏） |
| 搜索联想/高亮 | `search.suggest` / `search.highlight` |
| 代码块复制按钮 | `content.code.copy` |
| 右上角仓库链接 | `repo_url: https://github.com/suixinhub/knowledge-base` |
| 页脚版权 | `copyright: 文本` |
| 自定义域名 | 仓库 Settings → Pages → Custom domain（并在域名商加 CNAME 记录） |

**注意**：`theme.features` 是列表，增删整行即可；`palette` 是对象列表，动它要小心缩进层级。

## 十三、安全与隐私红线

仓库是**公开**的，任何人可以读、可以克隆、可以看历史提交（包括已删除的内容）。

**绝对不要放**：

- 真实客户名称、供应商名称、合同金额
- 公司内部系统截图、内部流程文件原文
- 个人身份信息（身份证、手机号、住址、家庭成员）
- 密钥、Token、密码（哪怕后来删了，历史里还在）
- 未公开的产品规划、财务数据

**需要放这类内容时**：

1. 另建一个**私有仓库**（私有仓库不开 Pages，只能在 GitHub 网页端看，或本地 clone 看）
2. 或做脱敏：把客户改成"A 公司"、金额改成区间、截图打码
3. 已经误传了：删文件不够，必须用 `git filter-repo` 清理历史，或直接删库重建。**这种事一定要先找我，不要自己动手**

## 十四、速查表

```
# 拉取最新
git pull

# 提交全部改动并推送
git add -A && git commit -m "docs: 说明" && git push

# 本地预览（自动刷新）
mkdocs serve

# 本地构建一次（检查有没有报错，不发布）
mkdocs build

# 查看最近 5 次提交
git log --oneline -5

# 查看工作区改动
git status

# 查看某篇文档改了什么
git diff docs/某篇.md

# 代理拦截时推送
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY \
  GIT_TERMINAL_PROMPT=0 git -c http.proxy= push origin main

# 触发一次重新构建（空提交）
git commit --allow-empty -m "chore: 重新构建" && git push
```

|---|---|
| https://suixinhub.github.io/knowledge-base/ | 知识库网站 |
| https://github.com/suixinhub/knowledge-base | 仓库首页 |
| .../actions | 构建状态 |
| .../settings/pages | Pages 发布配置 |
| .../settings | 仓库设置（含可见性切换） |

## 十五、日常节奏建议

不要为了"建知识库"而写，要为了"下次不用重新想"而写。

| 时机 | 动作 | 花费 |
|---|---|---|
| 做完一件复杂的事 | 把结论和判断依据写成一篇（方法+边界+坑） | 15 分钟 |
| 读到有用的东西 | 摘 3~5 条要点 + 一句"对我有什么用" | 5 分钟 |
| 同一个问题回答过两次 | 立刻写成文档，下次直接发链接 | 10 分钟 |
| 每月一次 | 翻一遍旧文档，删过时的、合并重复的 | 30 分钟 |
| 每季度一次 | 重组分类，看导航是否还合理 | 1 小时 |

判断一篇文档值不值得留，一个问题就够：**三个月后的我，会不会因为这篇文档少花半小时？** 会，就写；不会，就别写。
