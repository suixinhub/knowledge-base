    原理与架构¶

    一、核心思想：把"写内容"和"排版发布"彻底拆开¶

    传统知识库（Notion、语雀、印象笔记）把内容和排版存在一起：你在编辑器里看到什么，就存什么。代价是内容被锁在那个软件的数据格式里，离开软件就打不开，样式一改全站跟着变，历史版本也说不清。

    这个知识库走的是另一条路——内容只存纯文本，呈现完全交给程序生成：

    你写的          机器生成的
┌──────────┐   ┌──────────┐
│  .md 文本 │ → │  HTML 页面 │
│ （源）    │   │ （产物）  │
└──────────┘   └──────────┘
   长期保存        随时可丢弃重建

    这个分离带来三个后果，也是整个系统的价值来源：

    1. 内容不会死。.md 是纯文本，十年后任何编辑器都能打开，不依赖任何厂商。
    2. 样式可以随时换。改一行配置就能换主题、换字体、换配色，所有页面一起变，内容一个字都不用动。
    3. 产物可以随时丢弃。网站坏了不怕，源文件在，重新构建一次就恢复。

    二、三层架构¶

    ┌─────────────────────────────────────────────────────────────┐
│  第一层：内容源（Git 仓库 main 分支）                        │
│                                                             │
│   docs/*.md         ← 你写的正文                             │
│   docs/assets/      ← 图片、PDF 等附件                       │
│   mkdocs.yml        ← 网站结构、导航、主题、插件配置          │
│   requirements.txt  ← 构建环境依赖（锁版本）                 │
│                                                             │
│   特点：纯文本、可 diff、可回滚、任何编辑器可读写             │
└──────────────────────────┬──────────────────────────────────┘
                           │ git push 触发
┌──────────────────────────▼──────────────────────────────────┐
│  第二层：构建（GitHub Actions 云端机器）                     │
│                                                             │
│   pip install -r requirements.txt   ← 装 MkDocs + 主题       │
│   mkdocs build                      ← 编译成静态站点          │
│                                                             │
│   输入：Markdown + 配置                                      │
│   输出：site/ 目录（全站 HTML + CSS + JS + 搜索索引）         │
└──────────────────────────┬──────────────────────────────────┘
                           │ 推送到分支
┌──────────────────────────▼──────────────────────────────────┐
│  第三层：发布（gh-pages 分支 → GitHub Pages CDN）            │
│                                                             │
│   https://suixinhub.github.io/knowledge-base/               │
│                                                             │
│   特点：全球 CDN、HTTPS、无服务器、无数据库、永不下线         │
└─────────────────────────────────────────────────────────────┘

    关键点：第二层和第三层是完全自动的。你唯一需要操作的是第一层（写文件 + 推送）。

    三、一次推送到底发生了什么¶

    从你在命令行敲下 git push 到手机能看到新内容，中间发生 8 件事：

    步骤 发生位置 动作 耗时
    1 你的电脑 git push 把改动传到 GitHub 几秒
    2 GitHub 检测到 main 分支有新提交，读取 .github/workflows/ci.yml 即时
    3 云端容器 启动 Ubuntu 环境，checkout 拉取代码 ~5 秒
    4 云端容器 pip install -r requirements.txt 安装依赖（有缓存时很快） 10~30 秒
    5 云端容器 mkdocs build 编译全站，生成 site/ 3~20 秒
    6 云端容器 把 site/ 强制推送到 gh-pages 分支 几秒
    7 GitHub Pages 检测到 gh-pages 更新，分发到 CDN 节点 10~60 秒
    8 全世界 访问网址拿到新页面 即时

    全程通常 40 秒到 2 分钟。状态可以在仓库的 Actions 页面看到，绿勾=成功，红叉=失败（点进去看日志）。

    四、几个必须理解的机制¶

    1. Markdown 编译：文本 → 结构 → 样式¶

    .md 里的 # 一级标题、| 表格 |、- 列表 会被解析成 HTML 的 <h1>、<table>、<ul>，然后由主题的 CSS 决定长什么样。

    这意味着：你只管语义，不管样式。写 ## 二级标题 而不用操心它多大、什么颜色、多少个像素——那就是"内容与呈现分离"的具体体现。想调样式去改主题配置，不要在两篇文档里分别手写 HTML。

    2. mkdocs.yml 是网站的"骨架配置"¶

    它管四件事：

    配置块 作用 改错了会怎样
    site_name / site_url 站点名称与绝对地址 分享链接、SEO 会异常
    theme 主题、语言、配色、功能区开关 页面能出但样式崩
    plugins 搜索等能力 搜索失效
    nav 导航树结构 页面存在但导航里找不到

    nav 是最容易踩坑的地方：它是一份手写的目录清单，和磁盘上的文件夹是两套东西。你在 docs/ 里新建了文件但没写进 nav，页面会被构建出来（能通过 URL 直接访问），但导航里不会出现它——大部分人以为"没生效"，其实是漏了这一步。

    3. 目录结构 vs 导航结构¶

    系统里存在两个平行的结构：

    磁盘结构（物理）              导航结构（逻辑）
docs/                        nav:
├── index.md          →       - 首页: index.md
├── 供应链包装/        →       - 供应链包装:
│   ├── index.md      →           - 概览: 供应链包装/index.md
│   └── 包装主数据.md  →           - 包装主数据清单: 供应链包装/包装主数据.md
└── 关于/             →       - 关于本库:
    └── 原理与架构.md  →           - 原理与架构: 关于/原理与架构.md

    两个结构不强制一致，这是特性不是 bug：你可以把同一篇文档挂在不同导航位置，也可以调整导航顺序而不动文件。但为了长期可维护，建议保持两者同构——磁盘上看到什么顺序，导航就是什么顺序。

    4. 搜索是怎么做到"没有后端也能全文检索"的¶

    这是很多人第一次用会疑惑的点：静态站没有服务器，搜索怎么实现？

    原理是把索引提前烤进文件：

    1. 构建时，搜索插件扫描全站所有文档，切词、去掉停用词，生成一个 search/search_index.json（标题、正文片段、URL 的映射）。
    2. 用户打开网页时，这个 JSON 随页面一起下载到浏览器（几 MB，被 gzip 压缩后通常几百 KB）。
    3. 用户在搜索框输入时，浏览器里的 JavaScript（lunr.js）在本地内存里做匹配，不发出任何网络请求。

    所以搜索是瞬时的，也是完全离线可用的。中文能搜是因为配置里指定了 lang: [zh, en]，启用了中文分词支持——不加这一行，中文搜索会退化成一字一匹配，效果很差。

    代价是：文档非常多（几千篇）时索引文件会变大，首屏加载会慢。以目前的规模（十几篇），完全无感。

    5. 分支的分工：main 是源，gh-pages 是产物¶

    分支 内容 谁写 能不能手改
    main Markdown 源文件、配置、工作流 你（或我） ✅ 所有改动都在这里
    gh-pages 编译后的 HTML/CSS/JS GitHub Actions 自动覆盖 ❌ 手改会在下次构建时被冲掉

    永远不要手动编辑 gh-pages。它是可再生的产物，改它没有任何意义，而且下一次构建就没了。

    6. Git 在这里的角色：不只是备份，是"知识的演进史"¶

    普通网盘的版本历史是"按时间存的快照"，看不出改了什么、为什么改。Git 存的是差异（diff）+ 提交信息：

    commit a1b2c3d  docs: 新增包装主数据四类包装对照表
    + 新增 12 行表格
    - 删除 3 行过时字段说明

    这带来两个实际好处：

    • 回溯：某个结论被改过，能查到什么时候、改成了什么。知识库最怕的"我明明记得写过但现在不一样了"，在这里是可查的。
    • 协作与 AI 友好：任何工具（包括我）都能读到精确的差异，而不是整篇重写。批量改标题、统一格式这类操作，在纯文本 + diff 的结构上是安全的；在富文本数据库里几乎不可能。

    五、数据模型¶

    概念 对应实体 约定
    分类 docs/ 下的文件夹 一个文件夹 = 一个主题域，配一个 index.md 作概览
    页面 一个 .md 文件 文件名即 URL（中文可用，会自动编码）
    页面标题 文件内第一个 # 标题 显示在浏览器标签和搜索结果里
    附件 docs/assets/ 下按类型分目录 图片 assets/img/、PDF assets/pdf/
    内链 [文字](相对路径.md) 用相对路径，不要写死域名
    元信息 YAML front matter（可选） 如 tags、date，需配合插件才有实际效果

    六、为什么这个结构特别适合"人和 AI 一起维护"¶

    这不是附带的优点，而是这套方案的隐藏红利：

    1. 纯文本可批量处理。给 20 篇文档统一加一段说明、改一套术语，脚本一次跑完；富文本数据库里只能一篇篇点。
    2. 结构可预测。文件在哪、导航在哪、正文什么层级，规则固定，AI 不需要"看界面"就能改对。
    3. 改动可审查。每次修改在 git 里是一条 diff，改错了 git revert 就回去了，不存在"改坏了但不知道改了什么"。
    4. 不怕并发冲突。同一篇文档被两端同时改，git 会明确报冲突让你选，而不是像某些在线文档那样悄悄用后写的覆盖先写的。

    七、必须知道的边界¶

    任何方案都有它做不到的事，提前知道能省很多折腾：

    做不到 原因 替代做法
    评论、点赞、多人实时协同编辑 静态站没有后端和数据库 需要讨论就用聊天工具；要评论可接 giscus（基于 GitHub Discussions）
    按人分权限（这篇只给 A 看） Pages 只有"公开"或"私有仓库不发布"两档 敏感内容另建私有仓库，不发布
    在线表单、动态查询、数据库式检索 没有运行时 真有需求就上真正的应用，不要拿它硬扛
    毫秒级即时生效 每次改动要跑一遍构建 接受 1~2 分钟延迟；本地预览可以做到秒级
    大文件存储（视频） 仓库体积会膨胀，克隆变慢 视频放对象存储/网盘，文档里放链接
    所见即所得编辑器 它是"写 Markdown"的工具 用 Typora / Obsidian / VS Code 预览模式，或直接让我改

    一句话判断标准：如果需求是"把想法结构化成可检索的文档"，它是最优解；如果需求是"做一个有用户、有交互的系统"，它就不是这类工具，别硬用。

    八、可扩展的方向¶

    按性价比排序，以后想升级可以从这里挑：

    1. 自动标注更新日期（git-revision-date-localized 插件）——每页底部显示"最后更新于"，低成本高收益。
    2. 标签系统（tags 插件）——给文档加 tags: [包装, 主数据]，自动生成标签索引页，跨分类聚合。
    3. 博客模式（Material 内置 blog 插件）——适合写有时效性的记录（周报、读书笔记）。
    4. 评论（giscus）——基于 GitHub Discussions，无需自己的服务器。
    5. 自定义域名——买个域名指向 Pages，比 github.io 更正式。
    6. 多语言（i18n 插件）——同一主题中英双版本，一般个人库用不上。

    每加一项都要改 mkdocs.yml 并重新构建，建议一次只加一样，确认生效再加下一个。
